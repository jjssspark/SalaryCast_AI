TS-01. 카드들이 빈 회색 박스로 깨져 보임
영역 : FE
심각도 : High
상태 : 해결됨

증상 : Streamlit 앱의 카드들, 그러니까 홈 화면의 사용 방법·서비스 안내·다음 FA 주목 선수 카드, 검색 화면의 선수 정보 카드·연봉 카드·구단별 제시가 카드 같은 곳들이 전부 스타일링된 배경만 빈 채로 떠 있고, 실제로 들어가야 할 텍스트와 수치는 그 카드 바로 아래에 스타일 없는 맨 텍스트로 뚝 떨어져 나와 있었다.

재현 조건 : src/ui/pages.py의 render_home과 render_search에서 카드를 그릴 때 st.markdown으로 여는 태그 한 줄을 먼저 찍고, 내용은 그 뒤에 이어지는 여러 번의 st.markdown 호출로 채운 다음, 마지막에 또 다른 st.markdown 호출로 닫는 태그를 찍는 방식을 쓰고 있었다. 이 패턴을 쓴 카드는 예외 없이 항상 이 증상이 재현됐다.

원인 : Streamlit에서 st.markdown을 호출할 때마다 그 결과는 독립된 DOM 엘리먼트로 화면에 삽입된다. 즉 여러 번의 st.markdown 호출로 나눠 쓴 HTML 조각들은 실제 브라우저에서는 하나로 이어진 문서가 아니라 서로 남남인 별도의 블록들이다. 브라우저가 짝이 안 맞는 여는 태그 하나만 담긴 조각을 만나면 그 자리에서 곧바로 태그를 닫아버리기 때문에, 그 div는 카드 배경 스타일만 두른 채 내용 없이 텅 빈 박스로 남고, 진짜 내용은 완전히 다른 스타일 없는 엘리먼트로 떨어져 나온다.

시도했지만 안 된 것 : 처음에는 전역 CSS에 있던 column overflow hidden 규칙이 이 빈 박스를 가리려고 넣어둔 임시방편이라고 추측했다. 실제로 그 규칙이 있긴 했지만 빈 박스 자체를 없애주지는 못했고, 오히려 나중에 호버 팝업을 만들 때 컬럼 밖으로 튀어나오는 걸 막아버리는 부작용만 냈다. 증상을 가리는 CSS와 원인을 없애는 수정은 다른 문제였다.

해결방안 : 카드 하나에 들어갈 여는 태그, 내용, 닫는 태그를 파이썬에서 전부 하나의 문자열로 조립한 뒤 st.markdown을 단 한 번만 호출하도록 바꿨다. st.expander나 st.button처럼 실제 위젯을 안에 넣어야 하는 구간, 이를테면 구단별 제시가나 핵심 요소 분석 같은 곳은 애초에 하나의 div로 통째로 감쌀 수 없으므로, 억지로 감싸는 대신 그 구간을 감싸던 깨진 div 자체를 걷어내고 구획 제목만 별도로 스타일링해서 붙였다.

검증 : 홈 화면, 타자 찾기, 투수 찾기, 미래 FA 예정 선수 카드까지 브라우저에서 스크린샷으로 하나씩 확인했고 빈 박스 없이 전부 정상적으로 렌더링됐다.

배운 점 : Streamlit에서 unsafe_allow_html로 여러 조각짜리 HTML을 그릴 때는 부모를 여는 태그와 닫는 태그가 반드시 같은 st.markdown 호출 안에 있어야 한다. 태그를 여러 호출에 걸쳐 나누면 파이썬 코드는 아무 오류 없이 돌아가고 콘솔에도 아무 흔적이 안 남기 때문에, 이런 버그는 코드만 읽어서는 절대 못 잡고 실제로 브라우저에 띄워서 눈으로 봐야 발견된다.

TS-02. 카드 HTML 문자열이 들여쓰기 때문에 코드블록으로 그대로 노출됨
영역 : FE
심각도 : Low
상태 : 해결됨

증상 : TS-01을 고치던 도중, 홈 화면에서 여러 선수 카드 조각을 리스트로 모아 join한 뒤 하나의 문자열에 끼워 넣어 렌더링했는데, 그 부분만 카드 UI 대신 회색 배경에 고정폭 글꼴로 div class 같은 HTML 태그 문자열이 텍스트 그대로 노출됐다.

원인 : 반복문 안에서 만든 카드 조각 문자열들은 파이썬 소스 코드의 들여쓰기 위치 때문에 앞에 공백이 많이 붙어 있었다. 이 조각들을 이어붙여서 바깥쪽 문자열의 자리에 끼워 넣자, 최종 문자열에서 그 줄들이 네 칸 이상 들여써진 상태로 남았다. 마크다운은 줄 앞 공백이 네 칸 이상이면 그 구간을 코드블록으로 해석해서 HTML로 파싱하지 않고 글자 그대로 보여준다.

확인 방법 : 화면을 확대해서 보니 실제로 태그 문자열이 코드처럼 표시되고 있었다. 카드 조각들을 줄바꿈과 들여쓰기 없는 한 줄짜리 문자열로 다시 작성해서 합치자 곧바로 정상적인 HTML로 파싱됐다.

해결방안 : 여러 줄에 걸쳐 들여써져 있던 f-string 대신, 줄바꿈 없는 한 줄짜리 f-string으로 각 카드 조각을 다시 작성했다.

배운 점 : 같은 문자열도 소스 코드 어디서 만들어졌느냐에 따라 들여쓰기 수준이 달라지고, 그걸 그대로 이어붙이면 최종 결과물의 들여쓰기가 들쭉날쭉해진다. Streamlit이나 마크다운에 HTML을 주입할 때는 소스 코드의 보기 좋은 들여쓰기를 그대로 유지하려 하지 말고, 최종적으로 만들어질 문자열 자체가 몇 칸 들여써지는지를 항상 따로 신경 써야 한다.

TS-03. 소스 코드를 고쳐도 브라우저 화면이 그대로였음
영역 : Infra
심각도 : Low
상태 : 해결됨

증상 : 파일을 수정하고 저장한 뒤 브라우저를 새로고침해도 예전 화면이 그대로 나왔다. 파일은 분명히 바뀌었는데 변경 사항이 전혀 반영되지 않는 것처럼 보였다.

원인 : Streamlit은 server.runOnSave 옵션이 기본으로 꺼져 있어서, 소스 파일이 바뀌어도 자동으로 다시 실행하지 않고 화면 위쪽에 변경을 감지했다는 안내 배너와 재실행 버튼만 띄운다. 그런데 이 프로젝트의 전역 CSS에는 MainMenu와 footer와 header를 전부 숨기는 규칙이 있었고, 그 안내 배너가 header 영역에 그려지는 바람에 화면에서 아예 안 보이게 숨겨져 있었다. 재실행 버튼이 없었던 게 아니라 안 보였을 뿐이었다.

해결방안 : streamlit run 실행 시 server.runOnSave 옵션을 켜서 파일 변경을 자동으로 반영하게 했고, 그래도 파이썬 임포트 캐시나 pycache가 꼬였을 가능성을 없애기 위해 매번 프로세스를 완전히 종료하고 pycache를 지운 뒤 새로 띄우는 방식으로 확실하게 최신 코드가 반영되도록 했다.

배운 점 : 커스텀 CSS로 Streamlit의 기본 UI 요소를 숨기면, 그 요소가 원래 담당하던 시스템 알림까지 같이 숨겨질 수 있다는 걸 염두에 둬야 한다. 화면이 안 바뀐다고 코드가 잘못 저장된 건 아닌지 의심하며 시간을 쓰기 전에, 서버를 아예 새로 띄워서 그 가능성부터 지우는 편이 훨씬 빠르다.

TS-04. 컬럼의 overflow hidden 때문에 호버 팝업이 잘림
영역 : FE
심각도 : Medium
상태 : 해결됨

증상 : 홈 화면에서 다음 FA 주목 선수 카드에 마우스를 올리면 나타나야 할 프로필 팝업이 카드가 속한 컬럼 경계에서 그대로 잘려 나갔다.

원인 : 전역 CSS에 컬럼 엘리먼트의 overflow를 hidden으로 두는 규칙이 있었는데, 이건 TS-01의 빈 div 박스 버그가 있던 시절에 화면이 지저분해 보이는 걸 가리려고 넣어둔 임시방편으로 보였다. 이 규칙 때문에, 컬럼 경계 밖으로 튀어나오도록 절대 위치로 설계한 팝업이 컬럼 안쪽에서 잘렸다.

확인 방법 : 이 규칙을 visible로 바꾸고 다시 확인하니 팝업이 카드 왼쪽으로 온전히 튀어나와 보였고, 다른 화면에서 의도치 않은 가로 스크롤이나 레이아웃 깨짐도 생기지 않았다.

해결방안 : 컬럼의 overflow 값을 hidden에서 visible로 바꿨다. TS-01을 근본적으로 고쳐서 빈 박스 자체가 더 이상 안 생기게 됐기 때문에, 애초에 이 규칙이 가리려던 문제가 이미 사라진 상태라 안전하게 바꿀 수 있었다.

배운 점 : 눈에 보이는 증상만 가리는 임시방편 CSS는, 나중에 그 증상의 진짜 원인이 없어진 뒤에도 계속 남아서 전혀 상관없는 다른 기능의 발목을 잡을 수 있다. 이유를 알 수 없는 CSS 규칙을 마주치면 지우기 전에 왜 넣었는지부터 추적해보는 편이 안전하다.

TS-05. 네이버 스포츠 선수 사진이 전부 이니셜 아바타로만 표시됨
영역 : 외부API
심각도 : Medium
상태 : 해결됨

증상 : 검색 화면의 원형 선수 사진과 홈 화면 FA 카드의 호버 팝업 사진이 한 번도 뜬 적 없이 전부 이니셜 아바타로만 표시됐다. 에러는 전혀 나지 않았는데, 사진을 가져오는 함수가 이미 모든 예외를 조용히 무시하는 다단계 폴백을 갖고 있어서 실패해도 화면에는 아무 신호도 남지 않았기 때문이다. 원인을 하나씩 고칠 때마다 증상이 조금씩 형태를 바꿔가며 남아 있었다.

원인 : 네 가지가 겹쳐 있었다.
1) 파라미터 이름 변경 — 네이버가 통계 API의 정렬 파라미터 이름을 sortField에서 field와 direction으로 바꿨는데 코드는 옛 이름을 그대로 쓰고 있어서 API가 매번 400 에러를 돌려주고 있었다.
2) 응답 키 변경 — 파라미터 이름을 고쳐도 목록이 계속 비어 있었는데, 응답 구조 자체가 result 아래 players가 아니라 result 아래 seasonPlayerStats로 바뀌어 있었다.
3) pageSize 부족 — 위 두 개를 다 고친 뒤에도 전상현 같은 일부 선수는 여전히 사진이 안 떴는데, 요청할 때 pageSize를 200으로 잡아서 실제 KBO 투수 전체 등록 인원인 약 280명보다 적게 가져오고 있었다. WAR나 세이브나 홀드 어느 기준으로도 상위 200위 안에 못 든 중하위권 선수는 응답 자체에서 빠졌다.
4) Referer 차단 — 이미지 URL을 정상적으로 얻어도 img 태그로 그리면 브라우저가 기본으로 함께 보내는 로컬호스트 주소의 Referer 헤더를, 그 이미지를 호스팅하는 CDN이 도용 방지 목적으로 403으로 차단하고 있어서 사진이 깨진 아이콘으로 나왔다.

확인 방법 : 기존 파라미터 그대로 curl로 요청해보니 API가 정확히 field와 direction이 잘못됐다는 에러 메시지를 돌려줘서 올바른 파라미터 이름을 알 수 있었다.
파라미터를 고친 뒤 응답의 키 목록을 확인해서 seasonPlayerStats라는 실제 키를 찾아냈다.
pageSize를 200에서 500으로 올려서 같은 요청을 다시 보내보니 응답 인원이 200명에서 281명으로 늘었고 그 안에 전상현이 포함되는 것을 확인했다.
마지막으로 이미지 URL에 로컬호스트 주소를 Referer로 넣어 요청했을 때만 403이 나고 Referer를 아예 안 보내거나 네이버 도메인을 보내면 200이 나오는 것을 비교해서 도용 방지 차단이라는 걸 확정했다.

시도했지만 안 된 것 : 처음에는 이 개발 환경 자체가 외부망을 막고 있어서 그런 거라고 판단했다. 브라우저 자동화 도구로 네이버 스포츠 사이트를 직접 열려고 했을 때 별개의 이유로 차단당한 걸 이 네트워크 문제와 같은 것으로 착각한 탓이었다. 그런데 실제로는 요청이 서버까지 도달해서 정상적으로 400이라는 응답을 받고 있었으니, 이건 애초에 네트워크가 막혔다는 신호와는 맞지 않는 상황이었다.
또 파라미터 이름만 고치고 나서 다 됐다고 판단했다가, 응답 키가 여전히 안 맞아서 목록이 계속 비어 있다는 걸 뒤늦게 알아차렸다.
그다음엔 파라미터와 응답 키를 다 고쳤으니 끝났다고 생각했다가, 특정 선수가 계속 안 나온다는 걸 보고서야 pageSize 문제를 발견했다.

해결방안 : 사진을 가져오는 함수에서 요청 URL의 파라미터를 field와 direction으로 고치고 pageSize를 500으로 올렸다. 응답을 파싱하는 부분도 seasonPlayerStats 키를 먼저 확인하도록 고쳤다. 그리고 사진을 그리는 img 태그 두 곳 모두에 referrerpolicy를 no-referrer로 지정해서 브라우저가 Referer 헤더를 아예 안 보내도록 만들었다.

검증 : 새 파라미터와 pageSize로 curl 요청을 다시 보내 281명이 포함되고 전상현도 그 안에 있는 것을 확인했다. 이미지 URL에 Referer 없이 요청했을 때 정상 응답이 오는 것도 다시 확인했다. 마지막으로 Streamlit 앱을 재시작한 뒤 브라우저에서 최정, 이승현, 전상현 등 여러 선수를 실제로 조회하고 호버해서 이니셜 아바타 대신 진짜 프로필 사진이 뜨는 것을 눈으로 확인했다.

배운 점 : 400이나 404처럼 서버가 명확한 형식으로 응답하는 에러는 네트워크가 막혔다는 신호가 아니라 요청이 서버까지 도달했고 서버가 그 요청을 이해한 다음 거절했다는 신호다. 연결 자체가 막혔다면 타임아웃이나 연결 거부로 나타나지 이렇게 깔끔한 JSON 에러로 나타나지 않는다. 이 구분을 먼저 하지 않으면 엉뚱하게 환경 탓을 하다가 진짜 원인을 찾는 시점이 늦어진다.
문제를 하나 고쳤다고 바로 다 됐다고 판단하지 말고, 매번 실제로 목표로 삼은 대상이 정상적으로 나오는지까지 끝까지 확인해야 진짜로 해결한 것이다.
이미지가 안 뜨는 문제는 URL 자체가 틀렸을 때만 생기는 게 아니라 브라우저가 자동으로 붙이는 헤더 때문에도 생길 수 있다는 것도 다시 확인했다.
