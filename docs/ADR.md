아키텍처 결정 기록 (SalaryCast_AI)

이 문서는 SalaryCast_AI 프로젝트를 진행하면서 내린 주요 설계 결정과 그 이유를 남긴 기록이다. 코드만 봐서는 "왜 이렇게 했는지"가 안 보이는 결정 위주로 정리했다.

-----

ADR-01. 투수 역할(SP/SU/CL)을 별도 모델 3개가 아니라 단일 피처로 통합
상태 : 채택됨

배경 : 투수를 선발(SP)·셋업(SU)·마무리(CL)로 나누면 역할별로 중요한 스탯이 완전히 다르다(이닝 수 vs 홀드 vs 세이브). 역할별로 모델을 따로 학습시키는 방법과, 역할을 카테고리 피처 하나로 넣고 모델 하나에 다 학습시키는 방법 두 가지를 검토했다.

결정 : 역할별 모델 3개 분리 대신 pitcher_role 피처 하나로 통합했다.

이유 : KBO FA 투수 데이터는 연간 5~10명 수준으로 표본이 매우 작다. 이걸 SP/SU/CL 세 그룹으로 쪼개면 그룹당 표본이 한 자릿수로 줄어들어 어떤 모델도 패턴을 학습하기 어렵다. 반면 단일 모델에 역할을 피처로 주면 XGBoost 계열이 역할별 상호작용을 트리 분기로 알아서 학습할 수 있다.

결과 : save_3yr_avg >= 10이면 CL, hold_3yr_avg >= 10이면 SU, 나머지는 SP로 분류하는 규칙을 만들고 이를 라벨인코딩/원핫인코딩해서 피처에 포함시켰다.

ADR-02. 타자와 투수는 처음부터 완전히 분리된 모델로 학습
상태 : 채택됨

배경 : 타자와 투수는 평가 지표 자체가 다르다(OPS·wRC+ vs ERA·FIP·WHIP). 하나의 모델에 두 포지션을 다 넣고 position 피처로 구분하는 방법과, 아예 데이터셋과 모델을 둘로 나누는 방법을 검토했다.

결정 : 데이터 수집 단계부터 hitter_training / pitcher_training으로 CSV를 분리하고, 모델도 hitter_model.pkl / pitcher_model.pkl로 완전히 별도 학습·저장한다.

이유 : 두 포지션을 한 모델에 섞으면 공통 피처(war_3yr_sum, age_at_fa 등) 비중이 커지는 대신 각 포지션에만 의미 있는 피처(OPS, ERA 등)의 학습 신호가 약해진다. 표본 수가 적은 프로젝트 특성상(타자 80명, 투수 43명) 분리해서 각 모델이 해당 포지션의 패턴에만 집중하게 하는 편이 유리했다.

ADR-03. 총액·계약기간 등 데이터 누수 컬럼을 학습 피처에서 제외
상태 : 채택됨

배경 : 초기 v2 데이터셋에는 total_contract_amount(총액), contract_years(계약연수) 같은 컬럼이 그대로 들어 있었다. 이 컬럼들은 annual_avg_salary(연평균 계약금, 예측 타깃)와 total_amount = annual_avg_salary * contract_years 관계로 직접 연결돼 있어서, 모델이 정답을 거의 그대로 베끼는 결과를 만든다.

결정 : total_contract_amount, contract_years, player_name, position, team처럼 타깃을 간접적으로 드러내거나 학습에 불필요한 식별 컬럼을 전부 입력 피처에서 제외했다.

이유 : 데이터 누수가 있는 상태로 학습하면 검증 성능은 비정상적으로 높게 나오지만 실제 예측 상황(계약 전 시점)에서는 그 정보 자체가 존재하지 않으므로 모델이 무용지물이 된다. 이 발견 이후 데이터셋 버전을 v2 → v4로 올리며 누수 컬럼을 전량 재점검했다.

ADR-04. 모델은 선형회귀 → 랜덤포레스트 → XGBoost/LightGBM 앙상블 순으로 단계적으로 고도화
상태 : 채택됨

배경 : 수업 커리큘럼에서 배운 회귀·분류·앙상블 기법을 실제로 어떻게 적용했는지 보고서·발표에서 설명할 수 있어야 한다는 요구사항이 있었다. 처음부터 XGBoost만 쓸 수도 있었지만, 성능 비교와 설명 가능성 둘 다 필요했다.

결정 : 베이스라인은 선형회귀/다중선형회귀로 잡고, 랜덤포레스트로 비선형 관계와 피처 중요도를 확인한 뒤, 최종적으로 XGBoost·LightGBM 앙상블로 성능을 끌어올리는 3단계 구성을 채택했다.

이유 : 베이스라인 없이 바로 복잡한 모델을 쓰면 "왜 이 모델이 더 나은가"를 수치로 보여줄 수 없다. 각 단계마다 R²·MSE·RMSE를 비교표로 남겨서 성능 향상 근거를 명시적으로 기록했다.

ADR-05. app.py를 얇은 라우팅 계층으로 남기고 로직은 src/ 아래로 분리
상태 : 채택됨

배경 : 초기 버전은 app.py 한 파일에 데이터 로딩, 예측, UI 렌더링이 전부 섞여 있어서 파일이 계속 길어지고 있었다.

결정 : app/app.py는 페이지 라우팅만 담당하고, 데이터/모델 로딩은 data_loader.py, 피처 엔지니어링은 features.py, 예측은 predict.py, 구단 제시가 보정은 team_offers.py, 화면 렌더링은 src/ui/ 아래로 각각 분리했다.

이유 : 하나의 파일이 800줄을 넘기지 않게 하는 프로젝트 규칙과, 기능별로 같이 변경되는 코드를 같은 폴더에 묶는다는 구조 규약을 따른 것이다. 이 분리 덕분에 이후 UI 개선 작업(카드 렌더링, CSS, 호버 팝업 등)이 src/ui/pages.py와 src/ui/styles.py 안에서만 이뤄지고 예측 로직에 영향을 주지 않았다.

ADR-06. 시연 서비스는 별도 프론트엔드 프레임워크 대신 Streamlit으로 구현
상태 : 채택됨

배경 : 정해진 기간 안에 구단 관계자·야구 팬이 바로 써볼 수 있는 시연 서비스를 만들어야 했다. React 등으로 별도 프론트엔드를 구성하는 방법과 Streamlit으로 파이썬 안에서 바로 서비스형 UI를 만드는 방법을 검토했다.

결정 : Streamlit을 채택했다.

이유 : 모델 학습·추론 코드가 전부 파이썬이므로 별도의 API 서버나 프론트엔드-백엔드 통신 계층 없이 곧바로 화면과 연결할 수 있다는 게 가장 컸다. 로컬 IP·ngrok·Streamlit Community Cloud 세 가지 방식으로 발표 당일 시연 방법을 유연하게 고를 수 있다는 점도 일정상 유리했다.

제약 : Streamlit은 st.markdown 호출 하나하나가 독립된 DOM 엘리먼트로 렌더링되기 때문에 커스텀 HTML/CSS를 쓸 때는 여닫는 태그를 반드시 한 번의 호출 안에 넣어야 한다는 제약이 있다(자세한 내용은 docs/TROUBLESHOOTING.md TS-01 참고).

ADR-07. 구단별 제시가는 1차 연봉 예측과 분리된 2차 보정 로직으로 설계
상태 : 채택됨

배경 : "선수의 시장 가치(연봉)"와 "특정 구단이 이 선수에게 얼마를 부를 것인가"는 서로 다른 질문이다. 이 둘을 하나의 모델에 다 넣어서 구단별로 직접 예측하는 방법과, 선수 단위 예측 후 구단 조건으로 보정하는 방법을 검토했다.

결정 : 1차로 XGBoost 모델이 선수의 annual_avg_salary를 예측하고, 2차로 포지션 필요도(position_need_score)·샐러리캡 여유(cap_space_score)·윈나우 지수(win_now_score)를 반영한 규칙 기반 보정 공식으로 구단별 제시가 범위를 산출한다.

이유 : 구단별 데이터(10개 구단 × 포지션별 필요도)는 선수 단위 학습 데이터(80~140명)보다 훨씬 적어서 이 조건까지 모델에 함께 학습시키기엔 표본이 부족하다. 예측(모델)과 보정(도메인 규칙)을 분리하면 각 구단의 보정 계수를 발표 자리에서 사람이 이해할 수 있는 형태로 설명할 수 있다는 이점도 있다.
