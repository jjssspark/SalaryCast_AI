# 아키텍처 결정 기록 (SalaryCast_AI)

KBO FA 연봉 예측 프로젝트에서 내린 설계 결정 10건이다. 코드만 봐서는 왜 이렇게
했는지가 안 보이는 것 위주로 남겼다.

앞의 7건은 대부분 "표본이 적다"는 하나의 제약에서 갈렸고, 뒤의 3건은 작업을
진행하면서 앞의 판단을 뒤집거나 보완한 것이다.

## 한눈에 보기

| # | 결정 | 결정을 가른 이유 |
| --- | --- | --- |
| 01 | 투수 역할을 모델 3개가 아니라 피처 하나로 | 쪼개면 그룹당 표본이 한 자릿수 |
| 02 | 타자와 투수는 데이터셋부터 완전 분리 | 섞으면 포지션 고유 피처의 신호가 묻힘 |
| 03 | 총액·계약기간 등 누수 컬럼 제외 | 타깃을 그대로 베끼는 구조였음 |
| 04 | 선형회귀에서 시작해 단계적으로 올림 | 베이스라인 없이는 개선을 증명 못 함 |
| 05 | `app.py`는 라우팅만, 로직은 `src/`로 | 한 파일에 전부 몰려 계속 길어짐 |
| 06 | 프론트엔드 프레임워크 대신 Streamlit | 학습·추론이 전부 파이썬 |
| 07 | 구단 제시가는 예측과 분리된 2차 보정 | 구단 데이터가 모델 학습엔 너무 적음 |
| 08 | 성능 기준을 무작위 교차검증에서 시간 순서 검증으로 | 앱이 하는 일은 미래 예측 |
| 09 | 연봉을 시장 수준 대비 비율로도 예측해 섞음 | 트리가 연도를 외삽하지 못함 |
| 10 | 동명이인은 규칙 대신 선수 번호를 파일에 박음 | 규칙은 데이터가 한 줄만 바뀌어도 흔들림 |

성격별로 묶으면 이렇다.

- 표본 부족이 결정한 것: 01, 02, 07
- 데이터 신뢰성: 03, 10
- 설명 가능성: 04, 07
- 구조·도구: 05, 06
- 평가 방법: 08, 09

## ADR-01. 투수 역할(SP/SU/CL)을 별도 모델 3개가 아니라 단일 피처로 통합

> 쪼갤 표본이 없었다.

상태: 채택됨

### 배경

투수를 선발·셋업·마무리로 나누면 역할별로 중요한 스탯이 완전히 달라진다. 이닝 수,
홀드, 세이브가 각각 다른 역할에서만 의미를 갖는다.

역할별로 모델을 따로 학습시키는 방법과, 역할을 카테고리 피처 하나로 넣고 모델 하나에
다 학습시키는 방법을 검토했다.

### 결정

역할별 모델 3개 분리 대신 `pitcher_role` 피처 하나로 통합했다.

### 이유

KBO FA 투수는 연간 5~10명 수준이다. 이걸 세 그룹으로 쪼개면 그룹당 표본이 한 자릿수로
줄어들어 어떤 모델도 패턴을 학습하기 어렵다. 반면 단일 모델에 역할을 피처로 주면
부스팅 계열이 역할별 상호작용을 트리 분기로 알아서 학습한다.

### 결과

분류 규칙은 처음 안에서 두 번 바뀌었다. 처음에는 3년 평균 세이브 10 이상이면 마무리,
홀드 10 이상이면 셋업으로 갈랐는데, 절대값 기준이라 등판이 적은 시즌을 잘못 읽었다.
지금은 시즌마다 경기당 비율로 판정하고 갈래도 넷이다.

| 조건 | 역할 |
| --- | --- |
| 경기당 세이브 0.30 이상 | CL (마무리) |
| 경기당 홀드 0.25 이상 | SU (셋업) |
| QS가 있거나 경기당 3이닝 이상 | SP (선발) |
| 나머지 | RP (추격조·롱릴리프) |

선발 판정에 등판 방식을 직접 못 쓴 이유가 있다. 네이버 API의 선발 등판 수 필드가
100% 결측이라, 퀄리티스타트와 경기당 이닝으로 대신 판정한다.

서빙에서는 가장 최근 시즌의 역할을 그 선수의 역할로 쓴다. 불펜에서 선발로 전환한
선수를 옛 역할로 예측하지 않기 위해서다.

## ADR-02. 타자와 투수는 처음부터 완전히 분리된 모델로 학습

> 공통 피처가 커지면 포지션 고유 피처가 묻힌다.

상태: 채택됨

### 배경

타자와 투수는 평가 지표 자체가 다르다. 타자는 OPS와 wRC+, 투수는 ERA와 FIP, WHIP으로
본다.

하나의 모델에 두 포지션을 다 넣고 포지션 피처로 구분하는 방법과, 아예 데이터셋과
모델을 둘로 나누는 방법을 검토했다.

### 결정

학습 데이터를 만드는 단계부터 타자용과 투수용 CSV를 분리하고, 모델도 따로 학습해
따로 저장한다. 지금은 `models/hitter_v9_*.pkl`과 `models/pitcher_v9_*.pkl`이다.

### 이유

두 포지션을 한 모델에 섞으면 공통 피처(WAR 3년 합, FA 시점 나이 등)의 비중이 커지는
대신, 각 포지션에만 의미 있는 피처의 학습 신호가 약해진다. 표본이 적은 프로젝트라
분리해서 각 모델이 해당 포지션의 패턴에만 집중하게 하는 편이 유리했다.

### 지금 상태

FA 계약 210건 기준으로 학습 표본은 타자 136명, 투수 72명이다. 처음 이 결정을 내릴
때는 타자 80명, 투수 43명이었다. 계약 데이터를 2014년까지 넓히면서 늘었지만 여전히
작은 표본이고, 분리 결정을 되돌릴 이유는 생기지 않았다.

이 분리는 나중에 예상 못 한 곳에서도 값을 했다. 타자와 투수의 최적 설정이 서로
반대로 나왔기 때문이다. ADR-09를 참고.

## ADR-03. 총액·계약기간 등 데이터 누수 컬럼을 학습 피처에서 제외

> 검증 점수는 잘 나오는데 실제로는 쓸 수 없는 모델이 된다.

상태: 채택됨

### 배경

초기 데이터셋에는 계약 총액과 계약 연수가 그대로 들어 있었다. 이 둘은 예측 타깃인
연평균 계약금과 `총액 = 연평균 × 연수` 관계로 직접 연결된다. 모델이 정답을 거의
그대로 베끼는 구조였다.

### 결정

타깃을 간접적으로 드러내거나 학습에 불필요한 컬럼을 전부 입력에서 뺐다.

```
annual_avg_salary      타깃 그 자체
total_contract_amount  타깃 × 계약연수
contract_years         타깃과 총액을 잇는 값
player_name, player_id, team, position, pitcher_role, seasons_used   식별용
```

### 이유

누수가 있는 상태로 학습하면 검증 성능은 비정상적으로 높게 나온다. 그런데 실제 예측
상황은 계약 전 시점이라 그 정보가 존재하지 않는다. 결국 모델이 무용지물이 된다.

### 지금 상태

이 발견 이후 데이터셋 버전을 올리며 누수 컬럼을 전량 재점검했다. 지금은 계약 파일이
`fa_contracts_v7.csv`, 학습셋이 `hitter_training_v10.csv`와 `pitcher_training_v10.csv`다.
파일을 덮어쓰지 않고 버전을 올리는 규칙 덕분에 어느 시점에 무엇이 빠졌는지 되짚을 수 있다.

누수 제거 효과는 `output/reports/leakage_ablation.md`에 남겼다.

## ADR-04. 선형회귀에서 시작해 단계적으로 모델을 올림

> 베이스라인이 없으면 "더 낫다"를 숫자로 말할 수 없다.

상태: 채택됨 · 최종 구성은 아래 "지금 상태" 참고

### 배경

수업에서 배운 회귀·앙상블 기법을 실제로 어떻게 적용했는지 보고서와 발표에서 설명할
수 있어야 한다는 요구가 있었다. 처음부터 부스팅만 쓸 수도 있었지만 성능 비교와 설명
가능성 둘 다 필요했다.

### 결정

단계를 밟았다.

1. 베이스라인 — 선형회귀, 다중선형회귀
2. 릿지·KNN·결정트리 — 규제와 단순 모델의 한계 확인
3. 랜덤포레스트 — 비선형 관계와 피처 중요도
4. XGBoost·LightGBM — 최종 성능
5. 블렌딩 — 성격이 다른 두 모델을 가중 평균

### 이유

베이스라인 없이 바로 복잡한 모델을 쓰면 왜 이 모델이 더 나은지를 수치로 보여줄 수
없다. 단계마다 R²·MSE·RMSE·MAE를 비교표로 남겼다.

베이스라인이 실제로 값을 한 자리가 있다. 투수에서 규제 없는 선형회귀는 R²가 -2.08로
나온다. 평균값을 답하는 것보다 못하다는 뜻이다. 72명에 피처 47개인데 교차검증이라
한 번에 58명으로 학습하고, 원래 스탯과 그 백분위처럼 겹치는 피처가 많아 계수가
발산한다. 같은 선형 모델이라도 릿지는 0.11이 나온다. 왜 규제가 필요한지 보여주는
자리라 이 값을 지우지 않고 남겼다.

### 지금 상태

최종 구성은 부스팅 단독이 아니라 부스팅과 릿지의 블렌드다. 트리는 구간을 잘 나누고
선형은 전체 추세를 잘 잡아서, 섞으면 서로의 약점을 덮는다.

| 대상 | 최종 구성 |
| --- | --- |
| 타자 | LightGBM + Ridge 블렌드 |
| 투수 | XGBoost + Ridge 블렌드 |

여기에 ADR-09의 혼합이 한 겹 더 올라간다. 평가 기준도 R²에서 시간 순서 MAE로
바뀌었다. ADR-08을 참고.

## ADR-05. `app.py`를 얇은 라우팅 계층으로 남기고 로직은 `src/` 아래로 분리

> 분리해둔 덕분에 UI를 뜯어고쳐도 예측 로직이 안 흔들렸다.

상태: 채택됨

### 배경

초기 버전은 `app.py` 한 파일에 데이터 로딩, 예측, UI 렌더링이 전부 섞여 있어서 파일이
계속 길어지고 있었다.

### 결정

`app/app.py`는 데이터·모델을 한 번 읽어 컨텍스트를 만들고 페이지를 라우팅만 한다.
나머지는 역할별로 나눴다.

| 파일 | 역할 |
| --- | --- |
| `src/data_loader.py` | 데이터·모델 로딩 |
| `src/features.py` | 피처 엔지니어링 (학습·서빙 공용) |
| `src/predict.py` | 예측과 표본 부족 판정 |
| `src/serving.py` | 카드 한 장에 필요한 값 조립, 구단 제시가 |
| `src/explain.py` | 예측 근거 계산 |
| `src/ui/` | 화면 렌더링 |

### 이유

한 파일이 800줄을 넘기지 않게 한다는 규칙과, 기능별로 같이 변경되는 코드를 같은 폴더에
묶는다는 구조 규약을 따랐다.

이 분리 덕분에 UI를 전면 교체할 때도 작업이 `src/ui/` 안에서만 이뤄지고 예측 로직에
영향을 주지 않았다.

### 남은 것

`src/team_offers.py`와 `src/constants.py`는 앱 경로에서 쓰이지 않는다. 구단 제시가
계산이 `src/serving.py`로 옮겨 갔기 때문이다. 테스트가 아직 이 모듈을 보고 있어서
지우지 않고 뒀다. 정리 대상으로만 적어둔다.

## ADR-06. 시연 서비스는 별도 프론트엔드 프레임워크 대신 Streamlit으로 구현

> 학습·추론이 전부 파이썬인데 통신 계층을 새로 만들 이유가 없었다.

상태: 채택됨

### 배경

정해진 기간 안에 구단 관계자와 야구 팬이 바로 써볼 수 있는 시연 서비스를 만들어야
했다. 별도 프론트엔드를 구성하는 방법과, Streamlit으로 파이썬 안에서 바로 서비스형
UI를 만드는 방법을 검토했다.

### 결정

Streamlit을 채택했다.

### 이유

모델 학습과 추론 코드가 전부 파이썬이므로 별도의 API 서버나 통신 계층 없이 곧바로
화면과 연결할 수 있다는 게 가장 컸다. 로컬 IP, ngrok, Streamlit Community Cloud 세
가지로 시연 방법을 유연하게 고를 수 있다는 점도 일정상 유리했다.

### 치른 비용

Streamlit은 `st.markdown` 호출 하나하나가 독립된 DOM 엘리먼트로 렌더링된다. 커스텀
HTML을 쓸 때는 여닫는 태그를 반드시 한 번의 호출 안에 넣어야 한다. 이걸 모르고 짰다가
카드가 통째로 빈 박스로 깨졌다(TROUBLESHOOTING TS-005).

그 뒤로도 화면 쪽 문제가 이어졌다. 마크다운 들여쓰기 규칙 때문에 태그가 글자로 노출됐고
(TS-006), 기본 UI를 숨기는 CSS가 재실행 배너까지 숨겼고(TS-007), 임시로 넣은
`overflow: hidden`이 나중에 호버 팝업을 잘라먹었다(TS-008).

전부 파이썬이 오류 없이 도는 상태에서 화면만 틀렸다. 프레임워크를 쓰지 않고 얻은
속도의 대가가 이쪽으로 나왔다고 본다. 그래도 다시 골라도 같은 선택을 할 것 같다.
API 서버를 따로 세웠으면 이 시간보다 더 썼을 것이다.

## ADR-07. 구단별 제시가는 1차 연봉 예측과 분리된 2차 보정 로직으로 설계

> 시장 가치와 특정 구단의 제시가는 다른 질문이다.

상태: 채택됨

### 배경

이 선수의 시장 가치가 얼마인지와, 특정 구단이 이 선수에게 얼마를 부를지는 다른
질문이다. 둘을 하나의 모델에 넣어 구단별로 직접 예측하는 방법과, 선수 단위로 예측한
뒤 구단 조건으로 보정하는 방법을 검토했다.

### 결정

두 단계로 나눴다.

1. 모델이 선수의 연평균 계약금을 예측한다.
2. 규칙 기반 공식이 구단별 제시가 범위를 만든다.

```
제시가 = 예측 연봉 × (1 + 포지션 필요도 × 0.20
                      + 윈나우 지수 × 0.15
                      + 샐러리캡 여유 × 0.10)
범위 = 제시가의 ±10%
```

### 이유

구단별 데이터는 10개 구단 × 포지션별 필요도 수준이라, 선수 단위 학습 데이터(208명)보다
훨씬 적다. 이 조건까지 모델에 함께 학습시키기엔 표본이 부족했다.

예측과 보정을 분리하면 각 구단의 보정 계수를 사람이 이해할 수 있는 형태로 설명할 수
있다는 이점도 있다. 계수를 고치는 것도 모델 재학습 없이 된다.

### 한계

이 계수는 학습한 값이 아니라 정한 값이다. 실제 협상 데이터로 맞춘 게 아니라서 정확도를
주장할 수 없다. 화면에서도 예측 연봉과 구분해 보여준다.

## ADR-08. 성능 기준을 무작위 교차검증에서 시간 순서 검증으로 바꿈

> 2018년 계약을 맞히면서 2026년 계약을 이미 본 상태였다.

상태: 채택됨

### 배경

처음에는 5-fold 교차검증을 5회 반복한 값으로 성능을 쟀다. 표본이 작아 단일 분할은
점수가 흔들리기 때문이다. 그런데 이 방식은 무작위로 쪼개니, 2018년 계약을 예측할 때
2026년 계약이 학습에 들어간다.

앱이 실제로 하는 일은 미래 FA 예측이다. 과거로만 학습해 앞을 맞히는 조건에서 재야
실제 성능에 가깝다.

### 결정

시간 순서 검증을 1순위 기준으로 삼았다. 그해 이전 계약으로만 학습해 그해를 예측하고,
모델 선택과 피처 선택까지 폴드 안에서 다시 한다. 화면에 쓰는 오차 범위도 이 값이다.

### 결과

바꾸자마자 숨어 있던 문제가 드러났다. 거의 모든 해를 낮게 부르고 있었다. 타자 평균
-1.79억, 투수 -3.80억이었다. 무작위 교차검증에서는 이 편향이 안 보였다. 미래 데이터가
학습에 섞여 있으니 연봉 상승 추세를 이미 알고 있었기 때문이다.

이 발견이 ADR-09로 이어졌다.

### 비용

점수는 내려간다. 무작위 기준으로는 타자 0.724인데 시간 순서로는 0.627이다. 같은
모델의 같은 예측인데 채점 방식이 달라서 생기는 차이다. 낮은 쪽이 정직하다고 보고
그쪽을 화면과 문서의 대표값으로 쓴다.

## ADR-09. 연봉을 시장 수준 대비 비율로도 예측해 두 예측을 섞음

> 트리는 학습에 없던 연도를 외삽하지 못한다.

상태: 채택됨

### 배경

ADR-08에서 드러난 과소예측의 원인은 모델이 연도를 외삽하지 못하는 것이었다. 학습이
2021년까지면 2022년 입력을 2021년과 똑같이 취급한다. FA 시장은 해마다 오르는데 모델은
따라가지 못한다.

### 결정

예측을 두 벌 만들어 로그 공간에서 섞는다.

- base: 연평균 계약금을 그대로 맞힌다
- ratio: 연봉을 그해 시장 수준으로 나눈 값을 맞힌다. 시장 수준은 직전 3년 같은 유형
  FA 계약의 중앙값이다

ratio 쪽은 추세를 모델이 아니라 시장 지표가 담당하므로 외삽 문제를 피한다.

### 섞는 비율이 타자와 투수에서 반대로 나왔다

| 대상 | base 비중 | 피처 | 최근 계약 가중 |
| --- | --- | --- | --- |
| 타자 | 0.00 (ratio만) | 전체 | 반감기 3년 |
| 투수 | 0.75 | 상위 25개 | 없음 |

이유가 데이터에 있다. ratio의 분모인 시장 수준 중앙값이 타자는 연간 계약 6~15건이라
안정적인데, 투수는 1~9건이고 어떤 해는 한 건뿐이다. 못 믿을 분모로 나눈 값을 많이
쓰면 안 된다.

최근 계약 가중도 갈렸다. 타자는 옛 계약의 비중을 낮추면 좋아지는데, 투수는 표본이
72명뿐이라 비중을 낮추면 쓸 정보가 너무 줄어 오히려 나빠졌다.

ADR-02에서 모델을 나눠뒀기 때문에 이렇게 정반대 설정을 각각 줄 수 있었다.

### 결과

| 대상 | 시간 순서 R² | MAE | 편향 |
| --- | --- | --- | --- |
| 타자 | 0.627 | 3.26억 | -0.70억 |
| 투수 | 0.477 | 2.68억 | -0.40억 |

낮게 부르던 편향이 타자 -1.79억에서 -0.70억, 투수 -3.80억에서 -0.40억으로 줄었다.

### 설정을 고를 때 세운 기준

고르는 기준과 보고하는 수치가 같은 지표라 값이 그쪽으로 휜다. 그래서 규칙을 하나
정했다. MAE 차이가 0.01억 수준인 조합은 채택 근거로 쓰지 않고, 격자에서 한 칸만 튄
값도 쓰지 않는다. 여러 값이 한 방향으로 줄지어 있거나 봉우리가 하나로 뚜렷할 때만
바꾼다. 평평한 구간에서는 1위 칸이 아니라 가운데를 고른다.

실험 기록은 `output/reports/`의 `experiment_v9.md`, `experiment_topk.md`,
`experiment_recency_weight.md`에 있다.

## ADR-10. 동명이인은 판별 규칙 대신 선수 번호를 파일에 박아 해결

> 규칙이 지금 맞다는 것과 앞으로도 맞다는 것은 다르다.

상태: 채택됨

### 배경

KBO에는 같은 이름이 96쌍 있다. 타자 박건우만 셋이고, 김현수는 타자와 투수 양쪽에
있다. 이름으로 계약이나 FA 예정 정보를 붙이면 남의 기록이 딸려 온다.

처음에는 출전 경기 수와 소속팀을 대조하는 규칙으로 갈랐다. 그런데 이 규칙이 타자·투수로
나뉜 표 안에서 동작해서, 유형이 다른 동명이인은 구조적으로 못 걸렀다. 투수 김현수 카드에
타자 김현수의 16.67억 계약이 붙어 "고평가 계약"으로 표시됐다(TROUBLESHOOTING TS-012).

### 결정

두 단계로 처리했다.

1. 급한 불은 유형 대조로 껐다. 계약을 붙이는 쪽에서 계약 포지션과 선수 유형을 먼저 본다.
2. 그다음 계약 파일과 FA 예정 목록에 `player_id` 컬럼을 직접 넣었다. 이름 매칭 코드는
   서빙에서 없앴다.

### 이유

기존 규칙은 그 시점에 정답을 다 맞히고 있었다. 그런데 시즌 기록이 한 줄만 바뀌어도
결과가 달라지는 구조였다. 매번 다시 계산할 이유가 없는 값이라, 한 번 확정해 적어두고
조회만 하는 쪽이 낫다고 봤다.

판별 함수 자체는 안 건드렸다. 학습과 서빙이 같이 쓰는 함수라 고치면 학습 데이터 구성이
바뀌어 모델을 다시 학습해야 하는데, 이 문제는 계약을 붙이는 쪽에서만 막으면 충분했다.

### 검증

전수 점검 테스트를 먼저 세우고 수정을 되돌려 실제로 실패하는지 확인했다. 되돌린
상태에서 4건이 잡혔고, 그중 2건은 화면까지 오지 않아 눈으로는 못 찾을 것들이었다.

이 테스트는 지금도 마스터 전체를 돌며 유형이 어긋난 매칭을 잡는다. 새 동명이인이
들어와도 여기서 걸린다.

### 남은 것

한 건은 확정하지 못했다. 투수 김상수(2021 SK)는 시즌 기록 원본에 아예 없어서 비워
뒀고, 스크립트가 경고를 찍는다.

## 열 건에서 반복된 것

표본이 적다는 조건이 서로 다른 답으로 이어졌다. ADR-01은 역할별로 쪼개면 한 자릿수라
통합했고, ADR-02는 표본이 적으니 오히려 분리해 각자 집중하게 했고, ADR-07은 구단
데이터가 부족해서 모델 대신 규칙으로 뺐다. 같은 제약인데 통합·분리·제외로 갈렸다.

설명할 수 있는 형태를 계속 골랐다. ADR-04에서 베이스라인부터 쌓은 것도, ADR-07에서
보정을 규칙으로 남긴 것도 같은 이유다. 성능만 보면 다른 선택도 가능했지만 근거를
대야 한다는 조건이 설계를 바꿨다.

측정 방법을 바꾸자 설계가 바뀌었다. ADR-08에서 채점 기준을 시간 순서로 옮기니 그동안
안 보이던 편향이 드러났고, 그게 ADR-09를 낳았다. 모델을 어떻게 재느냐가 모델을 어떻게
만드느냐를 결정했다.

계산하지 말고 적어두는 쪽을 택한 적이 있다. ADR-10이 그렇다. 매번 다시 계산할 이유가
없는 값은 한 번 확정해 파일에 박는 편이, 아무리 잘 만든 규칙보다 안전했다.
