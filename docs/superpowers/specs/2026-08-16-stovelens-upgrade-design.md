## 1. 목적

기능을 실제로 쓸 만하게 만드는 것. 세 가지를 동시에 손댄다.

1. **예측을 믿을 수 있게** — 지금 화면에 뜨는 성능 수치가 실제와 다르고, 학습 과정에 타깃 누수가 있다
2. **찾고 싶은 선수를 찾을 수 있게** — 지금은 119명만 조회 가능한데 데이터에는 약 1,146명이 있다
3. **보고 이해할 수 있게** — 숫자만 있고 비교 기준이 없어 높은지 낮은지 판단이 안 된다

**목표**
- 화면에 뜨는 모든 성능 수치가 실제 학습 결과와 일치한다

## 4. 작업 영역 A — 모델 정직화

### A1. 피처 로직 단일화 (선행 조건)

`src/features.py`를 **유일한 피처 생성 지점**으로 만든다. `scripts/train_final_model.py`는 자체 `build_hitter_features` / `build_pitcher_features`를 버리고 `src/features.py`를 import 한다.

P2·P3·P5가 전부 이 이중화에서 파생됐으므로 이것을 먼저 한다.

**검증**: 학습 경로와 서빙 경로가 같은 선수·같은 입력에 대해 동일한 피처 벡터를 만든다 (테스트로 고정).

### A2. `market_level` 누수 제거

```
현재: market_level = 전체 데이터의 fa_year별 annual_avg_salary 중앙값
변경: market_level_prior = 해당 fa_year "이전" 연도들의 annual_avg_salary 중앙값
```

- 학습·서빙 동일 로직
- 2027년 예측 시 2026년까지의 중앙값 사용 → 미래 연도에도 계산 가능
- 최초 연도(2018)는 이전 연도가 없다. 해당 행을 학습에서 제외할지, 전체 중앙값으로 대체할지는 실험으로 결정하고 결과를 A9 표에 남긴다

### A3. 순위 피처 참조 분포 고정

`*_pos_pct`, `*_all_pct`는 현재 전체 데이터로 순위를 매긴다. 변경:

- CV 내부에서는 **train fold 분포로만** 순위 계산
- 최종 학습 시 전체 분포를 `models/{hitter,pitcher}_reference.pkl`로 저장
- 서빙은 이 저장된 분포에 신규 선수를 끼워 넣어 순위 산출

### A4. 학습 데이터 v7 통일

학습 스크립트가 `hitter_training_v7.csv` / `pitcher_training_v7.csv`를 읽는다.

### A5. 3년 평균 버그 수정

`recent3.sum() / 3` → `recent3.sum() / len(recent3)`.

- 학습 데이터가 실제 시즌 단순 평균으로 만들어져 있음을 확인함 (최형우 OPS `.9613` = 3시즌 단순평균)
- 시즌 수를 `active_seasons`로 함께 반환하고, 화면에 "최근 N시즌"으로 표기

### A6. 평가 정직화

모든 모델 평가에서 아래를 함께 산출·저장한다.

| 지표 | 설명 |
|---|---|
| R² (log) | `log1p(annual_avg_salary)` 기준 OOF R² |
| R² (원 스케일) | 억 원 단위로 역변환한 뒤의 R² |
| RMSE | 억 원 |
| MAE | 억 원 |
| n | 학습 표본 수 |

- `RepeatedKFold(n_splits=5, n_repeats=5)`로 분산 축소 (표본이 80/57로 작아 단일 5-fold는 시드에 민감)
- 타자·투수 meta pkl에 모두 저장 (P6 해소)

### A7. 예측 범위

OOF 잔차 분포의 10·90 분위수를 사용해 예측값에 범위를 부여한다. meta pkl에 저장하고 UI 게이지에 연결한다.

### A8. 앱의 성능 표시

`src/ui/pages.py`의 하드코딩 제거. meta pkl에서 읽어 표시한다. 값이 없으면 "측정 안 됨"으로 표기하고 숫자를 지어내지 않는다.

### A9. 누수 제거 전후 비교

`output/reports/leakage_ablation.md`에 아래 표를 남긴다.

| 조건 | 타자 R²(log) | 타자 R²(원) | 타자 RMSE | 투수 R²(log) | 투수 R²(원) | 투수 RMSE |
|---|---|---|---|---|---|---|
| 현행 (누수 포함) | | | | | | |
| 누수 제거 | | | | | | |
| 누수 제거 + 튜닝 | | | | | | |

**R²가 떨어져도 그대로 보고한다.** 숫자를 올리기 위해 누수를 되돌리지 않는다.

## 5. 작업 영역 B — 전 선수 검색

### B1. 검색 인덱스

새 모듈 `src/search.py`.

```
build_player_index() -> DataFrame
컬럼: player_name, player_type, team_latest, position, latest_year,
      season_count, fa_status, fa_year, initials
```

규모: 타자 460 + 투수 686 = 약 1,146명 (중복 제거 후 확정)

### B2. 초성 검색

한글 음절에서 초성을 추출해 `initials` 컬럼에 저장한다. 검색어가 초성만으로 구성되면 초성 매칭, 아니면 부분 문자열 매칭.

동명이인은 소속팀으로 구분해 표시한다.

### B3. 결과 모드 분기

| 모드 | 조건 | 화면 |
|---|---|---|
| A | `fa_contracts_v3.csv`에 FA 기록 있음 | 예측 vs 실제 + 고평가 / 적정 / 저평가 |
| B | `future_fa_candidates.csv`에 있음 | 예측 + 구단별 제시가 |
| C | A·B 둘 다 아님 | "지금 FA라면?" 가상 예측. 라벨 명시 |
| D | 표본 부족 | 예측 차단 + 사유 안내 |

**모드 D 기준**
- 타자: 최근 3시즌 합산 타수 < 150
- 투수: 최근 3시즌 합산 이닝 < 30

숫자를 내보내는 것보다 안 내보내는 편이 낫다는 판단. 실제 분포를 보고 임계값은 조정할 수 있다.

### B4. 큐레이션 명단 사용

`data/future_fa_candidates.csv`(42명)를 우선 로드한다. 이 파일에 없는 선수만 기존 "데뷔+10" 휴리스틱으로 보완하되, **휴리스틱 유래 항목은 position / fa_grade를 임의 값으로 채우지 않고 비워 둔다.**

### C1. 디자인 이식

### C2. 리그 비교 기준 계산

새 모듈 `src/league.py`.

```
league_reference(player_type) -> dict
  기준 풀: 최근 2시즌 · 타자 300타수 이상 / 투수 50이닝 이상
  반환: 지표별 mean, median, mean_percentile, 전체 분포
percentile_of(player_type, stat, value) -> float
```

확인된 타자 기준값 (2024–2025시즌, 300타수 이상 143명):

| 지표 | 평균 | 중앙값 | 평균의 백분위 |
|---|---|---|---|
| WAR / 시즌 | 2.80 | 2.52 | 55 |
| OPS | .798 | .791 | 54 |
| 홈런 / 시즌 | 14.0 | 13.0 | 55 |
| 타점 / 시즌 | 66.9 | 61.0 | 55 |

투수 기준값은 구현 시 동일 방식으로 산출한다.

**화면 표기 원칙**: 모든 스탯을 **시즌당 평균**으로 통일해 리그 평균과 같은 단위로 비교한다 (P11 해소). 모델 입력은 기존대로 3년 합계를 쓰되, 화면 표시만 평균으로 환산한다.

### C3. 지표 설명

- 지표명 옆 `?` 툴팁
- 화면 하단 상시 노출 글로서리: WAR, OPS, OBP, SLG, wRC+, ERA, FIP, WHIP

### C4. 파일 분리

## 7. 작업 영역 D — 선수 사진

### D1. 배치 수집으로 전환

런타임 외부 API 호출을 없앤다.

`scripts/collect_player_photos.py`
- 검색 인덱스 전체(약 1,146명)에 대해 **1회 배치 조회**
- 네이버 스포츠 API는 페이지 단위로 최대 500명을 반환하므로, 선수별 반복이 아니라 **연도·타입별 목록을 통째로 받아 이름 → URL 매핑**을 만든다
- 결과: `data/player_photos.csv`

```
player_name, photo_url, source, collected_at
<선수명>, <이미지 URL>, naver_api, 2026-08-16
```

`collected_at` 형식: `YYYY-MM-DD`

### D2. 누락 선수 목록 제공

찾지 못한 선수는 `output/reports/missing_photos.csv`로 출력한다.

```
player_name, player_type, team_latest, latest_year, season_count
```

시즌 수가 많은 순으로 정렬해, 노출 빈도가 높은 선수부터 채울 수 있게 한다.
**이 파일을 사용자에게 전달하고, 사용자가 채워준 사진을 받는다.**

### D3. 수동 보완 반영

사용자가 준 사진은 `data/player_photos_manual.csv`로 관리한다.

```
player_name, photo_url, photo_file
```

- `photo_url`과 `photo_file` 중 하나를 채운다. `photo_file`인 경우 `assets/photos/` 아래 파일명을 적는다
- 우선순위: **manual > api > 폴백(이름 첫 글자 배지)**
- 앱은 CSV만 읽는다. 외부 호출 없음

## 9. 리스크 · 미확인 사항

| 항목 | 내용 | 대응 |
|---|---|---|
| R² 하락 | 누수 제거 시 성능 수치가 지금보다 낮아질 가능성이 높다 | 그대로 보고. A9 비교표에 기록 |

| 2025 시즌 결측 | 홍창기의 2025 시즌 기록이 데이터에 없음(2022·2023·2024·2026만 존재). 다른 선수도 같은 결측이 있는지 미확인 | 구현 착수 시 결측 범위를 먼저 조사. 결측이 넓으면 "최근 3시즌"의 정의를 재검토 |
| 네이버 API | 정책 변경 시 사진 수집 스크립트가 실패할 수 있음 | 배치 수집이라 앱 동작에는 영향 없음. CSV가 남아 있으면 계속 표시됨 |
| 사진 저작권 | 네이버 이미지 URL을 핫링크로 사용 중 | 현행 유지. 수동 제공분은 사용자가 출처를 판단 |
| CSS `@property` | 카운트업이 구형 브라우저에서 동작하지 않음 | 최종값 즉시 표시로 폴백. 기능 손실 없음 |

## 10. 작업 순서

의존 관계에 따른 순서다. 각 단계는 앞 단계가 검증된 뒤 시작한다.

```
1. A1 피처 단일화        → 검증: 학습/서빙 피처 벡터 일치 테스트 통과
2. A2·A3·A4·A5 수정      → 검증: 누수·3년평균 테스트 통과
3. A6·A7·A9 재학습·측정  → 검증: meta pkl에 전 지표 저장, 비교표 생성
4. B1·B2 검색 인덱스     → 검증: 표본 20명 검색 성공
5. D1·D2 사진 배치 수집  → 검증: missing_photos.csv 산출 → 사용자 전달
6. C2 리그 기준 모듈     → 검증: 알려진 선수의 백분위가 수기 계산과 일치
7. C1·C3·C4 UI 이식·분리 → 검증: pytest 통과 + 앱 기동 + 4개 모드 스모크
8. A8·B3·B4 최종 연결    → 검증: 전체 검증 기준 통과
```
